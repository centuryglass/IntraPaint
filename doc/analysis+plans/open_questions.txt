- Layout issues are a persistent hassle, and making everything fit cleanly on small displays is challenging. How would you recommend addressing these changes at application scope?
- IntraPaint has a lot of weird idiosyncracies that make it undesirable to people who use established image editors. Identify all of these, tell me if/how you think IntraPaint should adapt to accomodate norms, and sketch out brief implementation plans for each.
- Asking users to install stability-matrix and worry about backend configuration is a major barrier to adoption. I don't want to bundle a full Stable Diffusion install, but ideally there should be at least one way to just push a button and have the backend stuff install itself with minimal user intervention. What would be the best path for implementing that?
- Using a huge bitmap for a 1-bit selection layer is inefficient and introduces significant lag on very large images. How would you recommend fixing that inefficiency without unnecessarily disturbing the rest of the codebase?
- I've got a WIP independent API wrapper library at ../sd-api-standalone. What would be the cleanest way to replace the existing src/api with that library?  You're allowed to recommend changes to both IntraPaint and that library itself.
- One of IntraPaint's biggest strengths is fine-grained context control: managing exactly what parts of the image are visible to the diffusion backend, and at what scale. Despite being better than most, the controls for managing this are still fairly clunky. Review my workflow documentation under doc/, and propose an improved interface for managing this functionality.
- Review IntraPaint's codebase from a software architecture perspective. What parts are legitimately good, and what ones are ill-advised? Is there anything that notably deviates from normal practices in ways that suggest I need to expand my knowledge?  Which parts would you recommend actually fixing?
- Test coverage is sparse and unevenly distributed, geometry_utils_test.py alone dominates CI runtime, and the areas with the most lurking bugs (transform tool, layer panel, responsive layout) have almost none. What should the long-term testing strategy be — coverage priorities, a shared fixture/base-class design, the golden-image maintenance workflow, handling flaky Qt/UI tests, and keeping CI time reasonable? This question is already partially addressed by the contents of test-wip, but contents of that directory aren't final.
- The transform tool's center-of-rotation and the two-way sync between on-canvas manipulation and the numeric panel fields are buggy and probably need a redesign. What's the right architecture for that shared transform state so the canvas, the panel, and the layer transform stay consistent?
- IntraPaint loses information when round-tripping ORA files authored elsewhere, and text layers get flattened. Design an approach for persisting non-destructive layer types (text via SVG or ORA XML extension, plus a future SVGLayer) and preserving non-standard tags/files from foreign ORA archives, following the TextLayer "convert to image" pattern.
- The config system is JSON-definition-driven with singleton classes, dynamically injected KEY attributes, and config_from_key routing. Evaluate this architecture end to end: is the definition-file + dynamic-attribute approach sound, should config_from_key be scrapped or made to enforce key exclusivity, and how well does it scale as options grow?
- Threading is scattered across AsyncTask, off-main-thread Config.set writes, the undo stack's re-entrancy lock, and generator backends that do work on worker threads. Audit the whole concurrency model for correctness and thread-safety, especially where worker threads touch shared image/config/undo state and hand results back to the UI thread.
- Rendering is built on QGraphicsScene/QGraphicsView, and there are recurring partial-alpha compositing glitches plus large-image lag. Is QGraphicsView the right foundation for a layered image editor, what's causing the compositing artifacts, and how should large-image performance be addressed without a ground-up rewrite?
- Distribution depends on per-platform native pieces — bundled libmypaint DLLs, the Cython image_fill extension, PyInstaller specs — and macOS/ARM support is incomplete. What's the cleanest strategy for packaging, building native deps, and supporting Windows/Linux/macOS(Intel+ARM) with minimal per-platform maintenance?
- The color picker is a lightly-modified Qt dialog and there's no foreground/background dual-color model that every other editor has. Design a color subsystem: a proper picker (RGB cube / wheel / OKLab), the FG/BG dual-color model shared across tools, and how it plugs into the existing config/cache color storage.
